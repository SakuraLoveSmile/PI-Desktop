# Expert Team, Plan Execution, and Chat Experience Implementation Plan

Status: planning only. T1-T7 are `未开始`. This document records a source-level plan, not an implemented or visually verified feature. The primary checkout, product source, running app, and user data have not been changed by this planning task.

## Baseline and decisions

- Surveyed `origin/main` at `35d690374` in the dedicated `codex/chat-modes-ux-plan` worktree. The primary checkout has unrelated local edits and is 241 commits behind this base; preserve it. The six UI screenshots are visual references from another interface, not evidence that PI-Desktop currently has a `Spec` mode or instructions to follow from the pictured conversation.
- PI-Desktop currently persists `Mode = "agent" | "plan" | "goal"`; the Composer cycles these values with one chip (`packages/shared/src/types/common.ts`, `apps/desktop/src/features/chat/composer/model.ts`, `ComposerToolbar.tsx`). Plan and Goal are host-authorized contract states of the same Agent, and approval returns the session to Agent before execution (`docs/spec/03-runtime/02-agent-runtime.md` section 5b). No new `spec` value is proposed.
- The transcript already separates an answer from `TurnProcess`, thinking, and tools, but renders the process before the answer and automatically opens it in Detailed mode (`AssistantTurn.tsx`, `turn-process.ts`). Existing title summarization already makes a separate model request after the first turn, but has no user switch (`session-title-runtime.ts`). The Composer already calculates usage, throughput, cache hit rate, and context capacity, but shows most of them only in `ContextUsageInspector`.
- The current approval surface is `PlanApprovalBar.tsx`, shown above the Composer only while a proposal is pending. Its artifact opener, permission choice, Reject, and Approve are reusable; it has no execution-model choice, durable scheduled state, or retained post-approval card. `PlanResolveRequest` has no provider/model field. `plan-dispatch.ts` resolves the session's current model at execution time, and `executeApprovedPlan()` appends its instruction to the existing runtime history. A menu-only change would therefore neither bind the selected model nor isolate planning context.
- Existing scheduled tasks run ordinary Agent prompts with `manual/hourly/daily/weekly` cadence. They do not execute an approved Plan/Goal snapshot. Their scheduler skips missed occurrences and cannot be reused unchanged for the requested one-time approval execution.
- Investigated the public MIT-licensed `@deepseek-ai/dsh-experimental-agent-team-profile@0.1.7-rc.2` package and its Team, tool, and UI packages. The profile is a Cordis patch, not a callable Team runtime; importing it into PI-Desktop would require the DSH Session, Subagent, projection, and persistence stack. Port the **current public Team behavior** into PI-Desktop ownership instead: Lead, durable named fresh/fork teammates, roster, queued/acknowledged mailbox, revisioned shared task board, nine team tools, waits/interrupts, and read-only roster/board/session UI. Do not add the Cordis runtime. If source is copied rather than reimplemented from behavior, retain its MIT notice and attribution.
- The DSH behavior reference is the exact public npm release `0.1.7-rc.2` of `@deepseek-ai/dsh-experimental-agent-team-profile`, `@deepseek-ai/dsh-experimental-agent-team`, `@deepseek-ai/dsh-experimental-tool-agent-team`, and `@deepseek-ai/dsh-experimental-client-ui-agent-team`; their package README, `lib/types/*.d.ts`, and profile `cordis.patch.yml` were read for this plan. Future implementers should fetch that version into an isolated scratch directory if the current `/tmp/dsh-*` extracts are gone; do not infer current DSH behavior from a newer unpinned package.
- Product choice: **execution profile** (`Agent` / `Expert Team`) is separate from **contract state** (`None` / `Plan` / `Goal`). The user explicitly selected full DSH Team behavior for this plan. PI-Desktop's `Task*` remains the standard Agent's in-process delegation, not a Team member. The Host-owned `session_collaboration` ledger and durable Session runtime are the nearest Team transport and lifecycle primitives; the official `pi.session-orchestrator` plugin remains a separate consumer and does not own Team truth. ADR 0239 already created an authenticated cross-session messaging exception to ADR 0165, but a built-in Team authority and sibling messaging still require a new ADR and an explicit extension of that exception.
- Screenshot 6 adds a post-plan card with a Goal switch, schedule action, and Execute action. The user confirmed that switching Goal on must create a **new Goal contract and approval**, and that scheduling means **one execution at a specified time**. The execution model must be independently selectable after the contract is drafted, without inheriting the planning model's conversation history.
- Screenshot 7's `No handler registered for 'pi-desktop/goalReport/retry'` is a source-level defect in the separate clean `feat/goal-completion-report` branch at `f3528adeb`: `goal-report-ipc.ts` defines the handler and `ipc/register.ts` imports `registerGoalReportIpc`, but `registerIpcHandlers()` never calls it. The blank white Retry button is also explained by `work-panel.css`: `--ds-accent` is light in dark mode, while `.goal-report-btn.primary` uses an undefined `--ds-accent-contrast` with a white fallback; the established `.btn-primary` uses `--ds-bg-primary` as contrasting text. These are IPC registration and contrast failures before successful Canvas report rendering; report body/layout remain unverified. The Goal report feature is absent from this plan worktree's `origin/main`, so T7 has an explicit branch dependency.
- The repository requires English code and documentation (`AGENTS.md` section 0 and `docs/spec/00-baseline.md`); this plan follows that rule. The final user-facing summary can remain Chinese. No local Electron instance, real provider, paid API, or UI E2E was used for this planning survey.

## Frozen user experience

1. **Composer axes.** Replace the cycling mode chip with a two-option anchored menu labelled `Agent` / `Expert Team` (localized). Immediately beside it, show a distinct contract control with `None`, `Plan`, and `Goal`; its selected `Plan` or `Goal` state is the PI-Desktop counterpart to the reference `Spec` chip. The existing permission control follows it. The right side keeps model/reasoning, prompt enhancement, and the single Send/Stop slot. Do not rename persisted Plan/Goal to Spec or collapse them into the team choice. The home and docked Composer use the same controls.
2. **Team behavior.** The profile is per session, defaults to `standard`, and survives restart. `team` applies to built-in pi Agent turns, including approved Plan/Goal execution; contract preparation remains one Agent with today's approval gate. The Lead can create at most eight permanently named direct teammates with fresh or completed-prefix fork context, message any member, wait for a later change, and interrupt a teammate's current turn. Each teammate is a distinct durable Session with its own transcript and may message peers and edit the shared task board, but cannot spawn or interrupt others. The task board supports at most 256 live tasks, dependencies with cycle/missing-dependency rejection, owner and `expectedRevision` CAS, all DSH update actions, tombstones, readiness, and advisory write-scope overlap warnings. Queue at most 64 undelivered messages per member and 65,536 UTF-8 bytes per framed message; store a stable sender/target/message identity before delivery, acknowledge only after the target Session records receipt, and deduplicate on recovery. An unreceived queued Team message resumes delivery once after app restart only while that Team is not paused; a message already bound to a target turn does not replay that turn. This Team-only recovery is distinct from the existing plugin-message and approved-execution no-replay fences and may create a provider request on startup. Roster/board events do not become ordinary conversation text or grant user authority. The UI shows member status, task board, warnings, and teammate Session navigation without giving the renderer write authority. The Lead produces one synthesis after team work; a small indivisible task may be handled by the Lead alone with an explicit explanation.
3. **Profile and compatibility.** A running or queued turn uses its captured profile; configuration changes during a turn are staged for the next turn. Switching a Lead back to Agent is blocked while any Team member is running/provisioning; after the Team is idle, switching pauses Team delivery and leaves its durable roster/board available if Team is selected again. Pending approval blocks Composer selectors; the separate execution-model picker on the proposal card remains available until approval/scheduling commits. Team can make multiple provider calls and its menu says so, including receipt of queued mail after restart for an unpaused Team. Team mode uses Team-specific tools, not `Task*` or the `SessionTask` plugin tool, so one member has one identity and one cancellation path; standard mode keeps both existing mechanisms unchanged. Every member uses Host permission ceilings and Agent admission; no Team tool elevates filesystem or model access. Trusted-extension agents and read-only Native Pi sessions cannot use Team; return an actionable error before a provider request, without silently falling back. User Stop on the Lead atomically marks the Team paused before aborting that Lead turn and Team-owned active member turns; pending mail remains stored but cannot claim a new target turn while paused, including after restart. The UI shows paused state and an explicit Resume Team action; a new Team prompt also explicitly resumes it. `interrupt_agent` aborts only the named teammate's current turn. Neither action releases task owners. Navigation does not stop either. Deleting a Lead session with a Team requires a confirmation that names the member and board impact, stops active member turns first, preserves member Sessions/transcripts as standalone conversations, then removes the Team relationship/board; deleting an attached member Session is blocked until the Lead is removed. A failed Team launch, approved execution, or teammate creation remains visible and never reports success or replays an already claimed turn merely on restart.
4. **Transcript hierarchy.** When an assistant answer exists, render its Markdown at the top of the turn as the primary, full-width reading block. Render a compact, lower-contrast `Process` disclosure after it, containing thinking and tool rows in their original order. When no answer exists yet, show live process status in its normal place; errors remain visible. Detailed/Compact still control what is expanded inside the secondary process, but neither puts process text ahead of an available answer. Preserve separate copy/search/minimap semantics, manual disclosure choice, keyboard focus, scroll anchor, failure badges, lazy tool-body parsing, and generated-image placement.
5. **Automatic titles.** Add a Settings > AI > Defaults switch for automatic short titles. The existing first-prompt fallback remains immediate and is never blocked by a model request. Default is **on** for compatibility; off makes no `session/summarizeTitle` call, keeps the fallback, and does not erase existing titles. On makes at most one background request per eligible session while its local preference store is available: set a per-session `autoTitleAttempted` marker before the IPC call and coalesce simultaneous triggers in memory. This marker remains set on failure or if the model returns the fallback verbatim, so restart does not generate another paid request. If local preference persistence is unavailable, keep the in-memory guard, allow a retry after restart, and report that limitation rather than claiming durable exactly-once behavior. Switching the setting off while a request is in flight ignores its result and preserves the current title; re-enabling does not retroactively retry marked sessions. Manual renames and already summarized titles always win, including after restart. Tighten the model-output acceptance to the prompt's short-title intent (at most 25 grapheme clusters for CJK or seven words for space-separated titles; reject an output that is only a URL or absolute path). An invalid or failed result leaves the fallback. The setting description discloses that the request sends a bounded excerpt of the first prompt and answer to the selected provider and may incur usage.
6. **Composer usage footer.** Add one quiet row immediately below the Composer shell, not another card: completed-turn output speed (`tok/s`), last visual turn's reported token total, latest provider request's cache hit rate, and context used/remaining percentage under the existing preference. Keep the detailed inspector as a click/keyboard popover from the context item. Use the existing usage and duration fields; do not claim a full-session total from a paged transcript. An unknown metric shows a dash with an accessible unavailable label, not a false zero; an estimated stopped-response speed is marked approximate. Before the first usage-bearing turn the row is absent. The row wraps cleanly at the 450px chat-column floor, remains inside the existing 768px content cap, and is included in the measured Composer dock height.
7. **Post-plan card and execution model.** Keep the proposal card visible from pending review through scheduled, running, and terminal execution, with the exact proposal title and a bounded Markdown preview. Its header uses the proposal's true Plan/Goal kind and an artifact opener; its footer holds the Goal switch, one-time schedule control, independent execution-model picker, permission choice, and Execute/Reject actions. Preview text is subordinate to the full artifact view. A model picked here applies only to this approval/execution and never changes the conversation's default model. The execution starts with project instructions, the approved permission snapshot, and the immutable approved artifact in a fresh execution-only runtime context, then writes its turn/events back to the originating conversation. No planning transcript, compaction checkpoint, or hidden prior user decision enters that model context. The execution instance survives session navigation and renderer reload; when it finishes, the ordinary Runtime is invalidated and the next user turn is rebuilt from durable Host transcript/execution metadata so it can see the execution result without rerunning tools. The card shows the selected model, due time where relevant, and a truthful execution status after commitment; controls lock when claimed/running.
8. **Goal and scheduling.** Goal off means the current Plan remains a Plan. Turning Goal on for a pending Plan does not relabel or approve the Plan: it starts regeneration of a new Goal contract from the immutable Plan artifact; the user reviews and separately approves that Goal. Failure leaves the Plan artifact available and shows a recoverable error; there is no automatic execution. A Goal card keeps Goal on. A one-time schedule is selected before approval, records an absolute instant and displayed local time zone with the chosen model and permission, and schedules exactly the approved snapshot. No recurring Agent prompt is created. The app must be running at the due time; the user confirmed that a due time missed while the app was closed must be marked `Missed` and require fresh confirmation, with no automatic catch-up on restart. A due launch interrupted after claim is `Interrupted` and also cannot replay. Cancel before dispatch disarms the schedule; after claim, existing stop/cancel semantics apply. Duplicate clicks, restarts, and renderer reloads must never produce a second execution.

## Shared contract and ownership

T1's shared interface is `ExecutionProfile = "standard" | "team"`. Session create/configure requests may omit it; the Host normalizes old and omitted values to `standard`. Normalized reads include it; unknown values fail validation. The Host owns durable profile, Team roster, board, mailbox, and Team-to-Session relationships. `Mode`, permission mode, proposal kind, and approval decision retain their meanings. Plan/Goal preparation uses standard tools without overwriting the stored Team profile; an approved execution binds the profile selected at approval. A profile/model choice made while a turn runs applies only to the next turn. At this baseline `SCHEMA_VERSION` is 19; assign additive migration versions in order and recheck current main before implementation. `TEAM_UNAVAILABLE`, `TEAM_UNSUPPORTED_AGENT`, stale task revision, invalid member, mailbox-limit, and authorization errors are stable shared codes with localized UI messages.

Team ID is the Lead Session ID; each member ID is a distinct durable Session ID. Only one flat Team belongs to a Lead; names never recycle. Canonical Host tables are `teams(team_session_id, revision, paused)`, `team_members(team_session_id, member_session_id, name, description, context_kind, phase, model binding, error)` with a unique name per Team, and `team_tasks(team_session_id, task_id, revision, subject, description, status, owner_session_id, blocked_by, write_scopes)` with tombstones; a Host transaction increments the Team revision and the roster/board projection reads those tables after restart. Extend the existing `session_collaboration_messages` ledger with an internal Team origin and Team ID instead of creating a second delivery ledger. Existing plugin records remain unchanged; only Host Team calls can set the Team origin, while plugin calls still require their correlated plugin identity. The Host authenticates the acting Agent's Session and Team membership through the existing correlated tool invocation, never a renderer-supplied sender. Team mail uses the existing Session admission/turn machinery with durable message IDs, an atomic target turn receipt, and source framing that identifies agent text as data rather than a user's authorization. Queue status is derived from the ledger; a bound target turn means delivered, even if the work later fails. Enqueue may persist during a pause, but target admission checks `paused` in the same Host serialization boundary; Resume clears it and drains in order. A new task-board snapshot must match `expectedRevision` and pass dependency graph validation before commit. Write scopes warn about overlap but never grant access; real writes still follow Host permissions and containment. Today's `PathMutex` is local to one runtime and is not a hard lock across durable member Sessions; Team does not promise atomic file isolation from peers, Bash, formatters, or external writers. The Lead must assign disjoint scopes and inspect the resulting diff.

| Existing mechanism | Team-mode rule | Compatibility boundary |
| --- | --- | --- |
| `Task/TaskWait/TaskList/TaskStop` | Hidden from Team member tool catalogs; Team uses durable member Sessions | Standard Agent keeps `Task*`, its 10-delegate cap, path mutex, report/context filtering, attribution, and tests unchanged. No `Task` record is silently converted into a Team member. |
| `pi.session-orchestrator` and `SessionTask` | Its tool is hidden in Team turns; its private worker registry is not Team state | The plugin remains available in standard turns. Existing plugin sessions and relationships stay readable and are not migrated without user action. |
| Host `session_collaboration` | Reuse authenticated session creation, permission ceiling, admission, cancellation, idempotency, and completion primitives behind a Team-specific authority | Existing plugin origin and worker limits do not become Team limits; plugin callers cannot forge Team membership. No second process-level execution engine. |
| Withdrawn A2A/Peer stack | Do not restore its tools, tables, broker, or protocol | The new ADR extends ADR 0239's scoped Session messaging exception for Team peers; it documents the deliberate departure from ADR 0165 without reviving unrestricted A2A. |

The source profile is **not** a PI-Desktop wire format. Match its observable contract, not Cordis registration or DSH private Session IDs. DSH itself is experimental, single-process, shared-checkout, flat-roster, and has no worktree/merge service, hard file lock, automatic task-owner release, nested Teams, or cross-process exactly-once mailbox guarantee. These are explicit limits of the requested port, not quietly omitted features. PI-Desktop must additionally reject unsupported remote/multi-host Team execution before provider access until the owning Host and runtime can guarantee one Team writer. A new ADR records alternatives, data migration, existing-feature compatibility, and the Team authority before implementation; if code is copied, keep the MIT license notice.

File ownership during implementation is exclusive. The main agent owns shared Composer integration (`Composer.tsx`, `ComposerToolbar.tsx`, `composer.css`, `responsive.css`), all touched i18n locale files, ADR/spec/E2E documentation, and final visual verification. Workers give the main agent their needed labels and CSS hooks; they do not edit those shared files concurrently. Each worker must read the nearest applicable `AGENTS.md`, the specified specs/ADRs, and current source/tests before coding. Local helper naming is discretionary; the behavior above is not.
